## 平日の簡単なrefactor優先ロジック

WORKFLOW-IMPLEMENT.mdのPhase 1で最初に判定する。平日はレビュー負荷を軽くするため、簡単なrefactor issueがあれば複数まとめて対応する。

**適用条件**: 実行日が日本時間で月曜〜金曜であること。

**対象候補の絞り込み**:
1. `needs-manual-follow-up`ラベル付きissueを除外する
2. `refactor`ラベルが付与されたissueのみを対象にする
3. 各issueの本文（「対応方針」セクション）から言及されている変更対象ファイル数を数え、**3ファイル以内**のものを一次候補とする（本文に具体的なファイル言及がなく判断できないissueは一次候補から除外し、通常フローに委ねる）
4. 一次候補を作成日（`createdAt`）が古い順に並べ、**最大3件**を対応対象として選定する

**Phase 2での再判定**: 選定した各issueについてPhase 2の「影響範囲（呼び出し元）確認」調査を行った結果、変更対象ファイルが3を超える、または影響を受ける呼び出し元が**5箇所を超える**と判明した場合は「簡単ではない」と判断し、そのissueを今回の対応対象から除外する（次点issueへの繰り上げは行わず、残った件数のまま進める）。

**平日でも対象0件の場合**: 通常時ロジック（1件選択）にフォールバックする。

**土日の場合**: 本ロジックは適用せず、常に通常時ロジック（1件選択）を使う。

## issue選択優先度ロジック（通常時・1件選択）

平日の簡単なrefactor優先ロジックが不成立だった場合（対象0件、または土日）に使う、1件のopen issueを選ぶための決定的ルール。

1. `needs-manual-follow-up`ラベル付きissueを候補から除外する
2. 残った候補をラベル優先度でソートする: `bug` > `test` > `refactor` > `documentation` > `enhancement`（不具合修正を最優先し、リスクの低い変更から着手する）
3. 同ラベル内は作成日（`createdAt`）が古い順を優先する（積み残し防止）
4. ラベルなしissueは、タイトル・本文の内容から種別を推定し`gh issue edit --add-label`で暫定ラベルを補完した上で、上記2〜3の優先度判定に組み込む
5. 複数ラベルを持つissueは、最も優先度の高いラベルで判定する
6. Phase 2の調査で選択中のissueの対応方針が無効と判断された場合、そのissueを候補から除外し、残った候補に対して1〜5を再適用して次点issueを選び直す（WORKFLOW-IMPLEMENT.mdのPhase 1・Phase 2参照）

## ラベル別対応分岐

WORKFLOW-IMPLEMENT.mdのPhase 2（調査）・Phase 3（実装方針）で使用する。

| ラベル | Phase 2での調査 | Phase 3方針 |
|--------|-----------------|-------------|
| `bug` | 再現手順の追跡、関連コードのRead | 最小差分での修正 |
| `refactor` | 影響範囲（呼び出し元）の洗い出し | 段階的変更、既存テストの維持を最優先 |
| `test` | 対象ViewModel/Managerの既存カバレッジ確認 | 新規テストファイル追加のみ（本体コードの変更は原則行わない） |
| `documentation` | doc/と実装の差分再確認 | doc/更新＋必要ならコメント補足 |
| `enhancement` | 関連仕様書（doc/spec/）の確認 | 新規実装、既存パターン踏襲 |

## 連続スキップ検知ルール

WORKFLOW-IMPLEMENT.mdのPhase 7で使用する。無限ループ防止のための仕組み。

`references/history.md`を確認し、該当issue番号についての直近2件の記録が両方とも「スキップ」（対応方針が確定できない・ビルド失敗3回・クロスレビュー上限到達での中断等）であれば、`gh issue edit <issue番号> --add-label needs-manual-follow-up`を実行する。これにより、以降のPhase 1の優先度選択で当該issueは候補から自動的に除外される。

**除外を解除したい場合**: ユーザーがGitHub上で`needs-manual-follow-up`ラベルを手動で外す運用とする（スキル側の自動解除は行わない）。
